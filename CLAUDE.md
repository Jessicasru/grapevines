# Grapevines

## What this is

Grapevines (working name) helps wine lovers plan trips to wine regions: a map of visitable wineries, with honest recommendations from the wine community. It is not a travel journal. Recommendations are public to everyone.

Live at mygrapevines.com. Current focus: Alsace, Champagne and Bourgogne.

## How to work in this repo

- Lovable syncs with `main`, so anything merged there goes live. Never push to
  `main`. Work on a branch and open a pull request.
- One task per pull request. Keep changes focused on that task.
- Each task comes with a "Done when" condition. Meet it, and say in the pull
  request how you checked.
- In the pull request, list anything Jessica must do by hand, such as applying
  a database change or adding a secret.
- If a task is unclear, ask in the pull request instead of guessing.

## Product principles

- No AI slop. No generated filler text, invented reviews, placeholder wineries
  or stock images. An honest empty state beats invented content.
- Every winery has a source and a verification date.
- Visitors give a Go / Skip verdict, not stars.
- Agents gather data; the review queue decides what goes live. Nothing an agent
  finds is published without review.

## Data rules

- Winery sources: OpenStreetMap, DATAtourisme, Overture.
- Credit OpenStreetMap on the map (ODbL). Credit DATAtourisme as a source
  (Licence Ouverte 2.0).
- Google Places is for enrichment only, never the source of the winery list.
  Never store Google photos.
- Don't scrape winery websites or copy their images without permission.
- Imports must be safe to rerun: a rerun creates no duplicates.

## Tech

Built in Lovable, with Supabase as the backend and Mapbox for the map.
The admin area (/admin) is open to Jessica's account only.

Read `AGENTS.md` before changing the map, the imports or the duplicate
review. It records why the code is built the way it is.

### Stack

- **App:** TanStack Start (React 19, TypeScript) with file-based routes and
  server functions. Vite builds it through `@lovable.dev/vite-tanstack-config`,
  which already includes the Vite plugins; don't add them again.
- **Data:** Supabase (Postgres, auth, database functions), read through
  TanStack Query.
- **Map:** Mapbox GL JS, loaded only in the browser.
- **UI:** Tailwind CSS 4, shadcn/ui (Radix), Framer Motion.
- **Tests:** Vitest, Testing Library, jsdom.
- **Packages:** Bun. `bunfig.toml` blocks versions less than 24 hours old.

### Folders

- `src/routes/` — file-based routes. `_map.tsx` is the layout that owns the
  map, `_map.index.tsx` is the home page, `_map.wineries.$id.tsx` is the
  winery detail, and `admin*.tsx` are the admin pages (wineries, import,
  duplicates, regions). `routeTree.gen.ts` is generated; don't edit it.
- `src/components/` — `WineMap.tsx` holds all Mapbox logic. `WineryDetail.tsx`
  shows a winery and takes Go / Skip verdicts. `ui/` holds shadcn/ui.
- `src/lib/` — `wine.ts` holds the data reads and the "recommended" rule,
  `auth.tsx` holds login state, and `*.functions.ts` are the server functions
  for imports and duplicate review. Tests sit beside the code they test.
- `src/integrations/supabase/` — Supabase clients and database types.
  Generated by Lovable; don't edit.
- `drizzle/migrations/` — one SQL file per database change.
  `drizzle/schema.ts` is empty on purpose.
- `supabase/config.toml` — the Supabase project ID.
- `data/` — region outlines and winery files to upload in /admin, with their
  sources. `scripts/data/` builds them (Python). See `data/README.md`.

### From Supabase to the map

1. `src/lib/wine.ts` defines each read as a `queryOptions`: regions, wineries
   and region boundaries. The wineries read includes each recommendation's
   verdict and leaves out merged duplicates.
2. The `_map` route loader fetches regions and wineries before the page
   renders. Components read the same cache, so the data loads once.
3. `_map.tsx` passes the wineries to `WineMap`, which turns them into a
   clustered GeoJSON source.
4. `isRecommended` in `wine.ts` decides which wineries count as recommended.
   Pins, cards and tests share this one rule.

Writes go the other way. Visitors log in to add a verdict or save a winery;
reading never needs a login. Admin imports (OpenStreetMap via Overpass, or
CSV) and duplicate review call server functions, which call database
functions that check `is_admin()` and match rows on their source, so a rerun
updates rows instead of adding them.

Admin access comes from the `is_admin` column on the `users` table. `/admin`
shows "not found" to everyone else.

### Run and test

```sh
bun install
bun run dev      # start the app
bun run test     # run the tests once
bun run lint     # check code style
```

`.env` holds the Supabase URL, the publishable key and the Mapbox token.
These are public values, and Lovable manages the file.

The database tests (`src/lib/*.integration.test.ts`) skip unless you set
`SUPABASE_DB_URL` plus `RUN_CSV_DATABASE_TESTS=1` or
`RUN_DUPLICATE_DATABASE_TESTS=1`. Some write to the database, so never point
them at the live one.

A database change goes in a new SQL file in `drizzle/migrations/`. List it in
the pull request; Jessica applies it by hand.
